Final Project – Autonomous Line-Following Robot with Obstacle Avoidance

**Overview**

This is the final project for the Introduction to Robotics course: a four-wheeled differential-drive robot that autonomously follows a black line marked on the floor which is the same as the mini project, and implemented to react to red and green boxes placed along the track as obstacles. Rather than just stopping or backing away when it meets an obstacle, the robot identifies the box's color with a custom-trained object detector and steers around it in the corresponding direction before rejoining the line, combining classic computer-vision line following with a small perception-and-planning pipeline split across two processors.

**How It Works**

The system is split across two boards that talk to each other over a serial link. A Raspberry Pi handles the "thinking": it grabs frames from a USB camera, runs OpenCV-based line detection and a YOLOv8 object detector, decides what the robot should do next, and streams the annotated camera feed as an MJPEG video over a small Flask server on port 5000 so the decision state can be watched live in a browser. The Pi sends the result as short text commands (Forward, Left, Right, AvoidLeft, AvoidRight, SearchLeft, SearchRight, Stop) over USB serial at 115200 baud. An ESP32 handles the "doing": it receives those commands and drives four independently PWM-controlled DC motors through H-bridges, and separately pings an HC-SR04 ultrasonic sensor every 100ms, reporting the distance back to the Pi as a `DIST:` line so the Pi always has a fresh read on what is directly ahead.

Line following itself is straightforward: the bottom ~45% of each frame is thresholded in HSV to isolate the black line, and the horizontal centroid of that mask decides whether the robot goes left, right, or forward; if the line disappears, the robot searches by turning opposite its last known direction until the line reappears. Obstacle handling is a four-phase state machine layered on top with strict priority. Once the ultrasonic sensor reports an object within 28cm, the robot stops and waits for YOLO — a YOLOv8n model fine-tuned on `greenbox`/`redbox`, reused from the earlier Object Detection assignment — to identify which color box is ahead: green sends it left, red sends it right. It then commits to turn → forward → turnback → recover: it pivots away for at least 0.6s using dedicated high-torque AvoidLeft/AvoidRight motor commands, drives straight past the box for 0.8s, mirrors that same turn duration in the opposite direction to square its heading back up, and finally drives straight for up to 1.6s (or until the line reappears, whichever comes first) before handing control back to normal line following.

**Requirements**

On the hardware side, the project needs an ESP32 dev board wired to four DC motors through H-bridge drivers (one PWM channel and two direction pins per motor), an HC-SR04 ultrasonic distance sensor, and a Raspberry Pi with a USB camera connected to the ESP32 over USB serial. On the software side, the Pi needs Python 3 with Flask, OpenCV (`opencv-python`), `pyserial`, and Ultralytics installed, plus the included `best.pt` weights (YOLOv8n, trained for 10 epochs at 320×320 on a Roboflow greenbox/redbox dataset). The ESP32 needs the Arduino IDE with the ESP32 board package and the ESP32Servo library to flash `sketch.ino`. Finally, the robot needs a track: a continuous black line on a light-colored floor, with a handful of green and red boxes placed beside the line as detour markers.

**Challenges**

Most of the hard problems here were about timing and coordination rather than any single algorithm. Early versions let a flickering YOLO detection re-trigger the avoidance turn mid-maneuver, adding extra untracked rotation every time a box entered and left the frame — fixed by locking the state machine so a new detection can't hijack a maneuver that's already in its forward/turnback/recover phase. The recovery phase also used to hand control straight back to line-following the instant the turn-back finished, which made the robot immediately trip the "line not seen" search logic before it had actually driven back over the line; that was solved by adding a forced-forward recovery window instead of an instant handoff. Steering torque was another issue — the gentle PWM speed used for everyday line corrections wasn't strong enough to pivot the robot around a box, so the avoidance turns were given their own higher-power motor commands. On the vision side, running YOLO at full camera resolution and frame rate on the Pi's CPU was too slow to keep the line-following loop responsive, so detection was throttled to a lower resolution and moved onto its own thread running independently of the main video loop.
